# K-Wellness CareOS 제품 계획

## 1. 제품 한 문장

K-Wellness CareOS는 산후관리 서비스를 예약·계약·배정·방문·기록·부모 확인·정산·재구매까지 연결하는 사업 운영 플랫폼이다.

초기 성공 기준은 기능 수가 아니라 다음 한 줄의 흐름이 빠르고 안정적으로 작동하는가이다.

> Customer → Contract → Assignment → Care Session → Care Event → Client Report

## 2. MVP 사용자와 핵심 과업

### 관리자 / 케어 매니저

- 오늘 진행되는 방문과 담당 관리사를 10초 안에 파악한다.
- 고객, 아기, 계약, 관리사를 등록한다.
- 계약 기간 내 방문 일정을 만들고 관리사를 배정한다.
- 미배정 일정, 종료 예정 계약, 확인이 필요한 기록을 본다.

### 관리사

- 휴대폰에서 오늘 방문 정보를 확인한다.
- 케어를 시작·종료한다.
- 수유, 기저귀, 수면, 체온, 산모 케어, 메모를 5초 안에 남긴다.
- 종료 전 오늘의 기록을 검토하고 리포트 초안을 만든다.

### 고객 / 보호자

- 아기의 오늘 상태를 이해하기 쉬운 요약으로 본다.
- 시간순 케어 활동을 확인한다.
- 관리사 메모와 승인된 일일 리포트를 확인한다.

## 3. 데이터 설계 원칙

- 사용자의 역할은 한 개로 고정하지 않고 `user_roles`로 분리한다.
- 고객, 보호자 계정, 아기를 서로 다른 엔터티로 분리한다.
- 계약과 관리사 배정을 분리해 대체 근무와 일정 변경을 지원한다.
- 하루 한 행짜리 차트 대신 `care_sessions → care_events` 이벤트 모델을 사용한다.
- 이벤트별 세부 정보는 검증 가능한 `JSONB payload`로 시작하고, 분석 수요가 확정되면 일부 컬럼을 정규화한다.
- 민감 케어 데이터와 리테일 CRM 데이터의 접근 범위를 분리한다.
- 모든 중요 변경은 `audit_logs`에 기록한다.

## 4. 단계별 개발 로드맵

### Phase 0 — 실행형 프로토타입 (현재)

- 역할별 핵심 화면
- 관리사 빠른 기록
- 고객 요약·타임라인
- 운영 대시보드
- 로컬 저장 기반 사용자 테스트

완료 기준: 실제 관리자 1명, 관리사 2명, 고객 관점 사용자 2명이 주요 흐름을 막힘 없이 수행하고 개선 의견을 남긴다.

### Phase 1 — Core Operations

- Supabase Auth 연결
- 사용자 초대와 역할 관리
- 고객, 보호자, 아기 CRUD
- 서비스 패키지와 계약
- 방문 일정과 관리사 배정
- Row Level Security와 감사 로그

완료 기준: 관리자가 실제 고객 1명의 계약과 1주 일정을 만들고 관리사가 자신의 일정만 볼 수 있다.

현재 로컬 프로토타입에는 이메일/ID 로그인, 고객·관리사 회원가입, 필수 동의, 관리사 관리자 승인, 2·3·4주 일정 배정, 고객 ID·배정 기간 기반 화면 제한이 구현되어 있다. 운영 배포 시 `003_auth_approvals_access.sql`의 Supabase Auth·RLS 정책으로 서버에서 동일한 제한을 강제한다.

### Phase 2 — Care Logging

- 세션 시작·종료의 서버 저장
- 케어 이벤트 CRUD
- 네트워크 불안정 시 임시 저장·재전송
- 특이 관찰 플래그와 관리자 확인 상태
- 관리사 일일 리포트 검토·승인

완료 기준: 한 번의 실제 케어 근무를 종이 기록 없이 완료하고 누락·중복 여부를 관리자가 확인한다.

### Phase 3 — Client Experience

- 고객 로그인
- 승인된 타임라인과 일일 요약
- 메시지와 알림
- 동의서와 문서
- 데이터 보관·삭제 요청 흐름

완료 기준: 고객이 자신의 가족 데이터만 보고, 관리사가 승인한 리포트를 모바일에서 확인한다.

현재 로컬 프로토타입에서는 고객 본인 차트, 관리자 승인 리포트 전달, 브라우저 인쇄를 이용한 PDF 저장과 배송 상태 확인까지 검증할 수 있다. 운영 PDF는 서버에서 생성한 뒤 비공개 Storage의 짧은 만료시간 서명 URL로 제공한다.

### Phase 4 — Admin Operations

- 리드 파이프라인
- 결제 상태 추적
- 급여 계산용 근무 집계
- 운영 KPI와 내보내기
- QuickBooks 등 외부 회계 연동 준비

### Phase 5 — Retail & CRM (실행형 프로토타입 구현 완료)

- 상품, 바코드, 재고 이동
- 외부 POS 연동
- 고객 구매 이력
- Care → Beauty 고객 여정 자동화

현재 로컬 프로토타입에서는 Beauty·유아용품 카탈로그, 고객 연결 POS, 주문, 재고 이동, 구매 이력, 통합 분석까지 작동한다. 운영 전환 시에는 `002_retail.sql`을 기준으로 Supabase에 연결하고, 실제 결제는 Stripe 또는 Shopify POS에 위임한다.

### Phase 6 — AI Assistance

- 케어 이벤트의 자연어 일일 요약 초안
- 관리자용 주의 항목 요약
- 관리사 검토가 필수인 리포트 초안
- 의료적 판단이나 자동 진단은 범위에서 제외

## 5. 다음 회의에서 확정할 항목

1. 실제 첫 운영 지역과 서비스 시간/요금 체계
2. 고객 한 명에 연결될 수 있는 보호자 수
3. 관리사 교대·대체 근무 규칙
4. 기록이 필수인 항목과 선택 항목
5. 고객에게 즉시 공개되는 기록과 관리자 승인 후 공개되는 기록
6. 이상 체온 등 주의 기준의 책임 주체와 안내 문구
7. 영문·한글 사용 비율과 현장 관리사의 주 사용 언어
8. HIPAA 적용 가능성, 동의서, 보관 기간, 데이터 삭제 정책

## 6. 권장 기술 전환

현 프로토타입에서 화면과 기록 흐름이 확정되면 다음 구조로 전환한다.

- Frontend: Next.js + TypeScript + Tailwind CSS + shadcn/ui
- Backend: Supabase PostgreSQL + Auth + Storage + Realtime + Edge Functions
- Hosting: Vercel
- 결제: Stripe 또는 기존 결제/POS와 연동
- 이메일: Resend 등 트랜잭션 메일 서비스
- SMS: Twilio 등, 고객 동의·수신 거부 정책과 함께 적용

프론트엔드 프레임워크 전환 전 사용자 테스트를 하는 이유는, 현장 피드백으로 정보 구조가 바뀔 가능성이 크기 때문이다. 확정 전 복잡한 백엔드를 연결하면 수정 비용이 커진다.
